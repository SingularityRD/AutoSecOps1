## Overview

AutoSecOps supports built-in OAuth integrations and custom OAuth providers. OAuth integrations expose tokens through secret expressions.

![OAuth integrations](/img/integrations/oauth-integrations.png)

## Grant types

OAuth grant types:

- Delegated access (`authorization_code`): AutoSecOps stores a user token after a user completes the OAuth login flow.
- Client credentials (`client_credentials`): AutoSecOps stores a service token for server-to-server access.

## Configure a provider

Built-in OAuth integrations are listed on the Integrations page. For custom OAuth, use Add integration → OAuth provider (or Add custom OAuth provider under Custom OAuth).

Most providers require these fields:

- Client ID
- Client secret
- Authorization endpoint
- Token endpoint
- Scopes

After you save a custom provider, connect it (complete the OAuth flow) when using delegated access so AutoSecOps can issue tokens.

## Redirect URI

Delegated access (`authorization_code`) requires a redirect URI registered in the provider's OAuth app. AutoSecOps uses one redirect URI for every OAuth provider, built-in or custom:

```
<PUBLIC_APP_URL>/integrations/callback
```

`PUBLIC_APP_URL` is the URL you use to reach the AutoSecOps UI, so the redirect URI looks like `https://<your-autosecops-host>/integrations/callback`. Self-hosted deployments set it through the `AUTOSECOPS__PUBLIC_APP_URL` environment variable; see [Environment variables](/self-hosting/environment-variables). The integration's configuration dialog also shows the exact value with a copy button.

Register the URI as a Web platform redirect URI (reply URL) in the provider's app registration before you connect. If it is missing or does not match exactly, the provider rejects the login flow. Microsoft Entra ID reports this as `AADSTS900971: No reply address provided` or `AADSTS50011: The redirect URI specified in the request does not match`.

Client credentials (`client_credentials`) has no login flow and needs no redirect URI.

## OAuth and actions

Registry actions reference OAuth integrations but do not create them. Configure a built-in or custom provider in Integrations first, then declare `RegistryOAuthSecret` (Python) or `type: oauth` (YAML) so the action requires that integration at runtime. See the OAuth declaration syntax and examples for [Python UDFs](/custom-actions/python-udf#python-udfs) and [YAML templates](/custom-actions/yaml-template#secrets).

## OAuth and MCP

Remote MCP integrations can use an existing OAuth integration. For custom remote MCP servers:

1. Create a custom OAuth provider.
2. Connect that provider.
3. Create an MCP integration and attach the connected OAuth integration.

## FAQ

<AccordionGroup>
  <Accordion title="Can my custom action create an OAuth integration?">
    No. `RegistryOAuthSecret` and YAML `type: oauth` entries declare that the action *requires* an existing OAuth integration — they do not register one. Create the integration from [Configure a provider](#configure-a-provider) (or [contribute a built-in provider](#how-do-i-contribute-a-built-in-oauth-provider)). Once it exists, your action can reference its tokens via `${{ SECRETS.<provider_id>_oauth... }}`.
  </Accordion>

  <Accordion title="How do I contribute a built-in OAuth provider?">
    Out-of-the-box providers are implemented in the AutoSecOps app and get stable IDs (for example `slack`, `google_drive`) without the UI `custom_` rule.

    1. Subclass `AuthorizationCodeOAuthProvider` or `ClientCredentialsOAuthProvider` under `autosecops/integrations/providers/`. See `slack/oauth.py` for a full example.
    2. Register the class in `_PROVIDER_CLASSES`.
    3. Keep the `packages/autosecops-registry` registry package aligned: same `provider_id` and `grant_type` in `RegistryOAuthSecret` (Python) and `type: oauth` entries (YAML) so actions resolve the same integration as the UI.
  </Accordion>
</AccordionGroup>
