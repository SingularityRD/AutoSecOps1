The Helm chart lives in the AutoSecOps repository at `deployments/helm/autosecops`. Install it from a checkout or package it into your own OCI registry.

## Prerequisites

- Kubernetes 1.30+
- Helm 3.12+
- `kubectl` configured for your target cluster
- PostgreSQL 15 or newer with pgvector (Amazon RDS, Cloud SQL, or [CloudNativePG](#cloudnativepg))
- Redis (Amazon ElastiCache, Memorystore, or similar)
- S3-compatible object storage (Amazon S3, MinIO)
- Temporal (self-hosted cluster or Temporal Cloud)
- A NetworkPolicy-capable CNI if you keep `networkPolicy.enabled: true`
- `openssl` for generating secrets

## What the chart deploys

| Component | Kind | Port | Notes |
| :-------- | :--- | :--- | :---- |
| `api` | Deployment, Service | 8000 | HTTP probes on `/health`. |
| `worker` | Deployment | none | Temporal DSL worker. |
| `executor` | Deployment | none | Action executor, `direct` or `nsjail` backend. |
| `agent-worker` | Deployment | none | Temporal agent worker. |
| `agent-executor` | Deployment | none | Agent runtime, `direct` or `nsjail` backend. |
| `mcp` | Deployment, Service | 8099 | Optional (`mcp.enabled`). |
| `litellm` | Deployment, Service | 4000 | Optional (`litellm.enabled`). |
| `ui` | Deployment, Service | 3000 | Next.js frontend. |
| `caddy` | Deployment, Service, ConfigMap | 8080 | Optional router with the same routes as the Docker Compose `Caddyfile`. |
| `migrations` | Job | none | `alembic upgrade head` as a `pre-install,pre-upgrade` hook. |

Every Deployment can add an HPA (`<component>.autoscaling`) and gets a PodDisruptionBudget (`<component>.pdb`) when it runs more than one replica. The chart adds an ingress NetworkPolicy per component: Caddy accepts traffic from `networkPolicy.caddyIngressFrom` (every source by default), the UI accepts only Caddy, the API, MCP, and LiteLLM accept only pods of the same release, and workers and executors accept no inbound traffic. Egress stays open because workflows and agents call integrations you choose.

## Secrets management

The chart reads every credential from Secrets you create. It never renders a secret value into a manifest.

<GenerateSecrets />

```bash
kubectl create namespace autosecops

kubectl -n autosecops create secret generic autosecops-core \
  --from-literal=dbEncryptionKey="$(openssl rand 32 | base64 | tr -d '\n' | tr '+/' '-_')" \
  --from-literal=serviceKey="$(openssl rand -hex 32)" \
  --from-literal=signingSecret="$(openssl rand -hex 32)" \
  --from-literal=userAuthSecret="$(openssl rand -hex 32)"

kubectl -n autosecops create secret generic autosecops-postgres \
  --from-literal=username=autosecops \
  --from-literal=password='<database password>'

kubectl -n autosecops create secret generic autosecops-redis \
  --from-literal=url='rediss://:<password>@<redis-host>:6379'
```

| Values key | Secret keys | Required |
| :--------- | :---------- | :------- |
| `secrets.existingSecret` | `dbEncryptionKey`, `serviceKey`, `signingSecret`, `userAuthSecret`; optional `licenseKey` (set `secrets.keys.licenseKey`) | Yes |
| `externalPostgres.auth.existingSecret` | `username`, `password` | Yes |
| `externalRedis.auth.existingSecret` | `url` | When Redis needs a password or TLS |
| `externalS3.auth.existingSecret` | `accessKeyId`, `secretAccessKey` | When the pods have no cloud identity |
| `externalTemporal.auth.existingSecret` | `apiKey` | Temporal Cloud only |

Override any key name under the matching `keys` or `auth` block. To sync these Secrets from a vault, use [External Secrets Operator](https://external-secrets.io) or your GitOps tooling to produce the same Secret names.

## Configure external services

### PostgreSQL

[Set up pgvector](/self-hosting/pgvector) before the first install; the migrations hook enables it.

```yaml
externalPostgres:
  host: "autosecops-db.example.internal"
  port: 5432
  database: autosecops
  sslMode: verify-full
  auth:
    existingSecret: autosecops-postgres
```

Keep `sslMode` at `require` or stricter for any network-reachable database.

#### CloudNativePG

To run PostgreSQL inside Kubernetes, use the [CloudNativePG](https://cloudnative-pg.io) operator. Load pgvector as an [image volume extension](https://cloudnative-pg.io/docs/1.30/imagevolume_extensions/#directly-in-the-cluster), then let a `Database` resource enable it in the application database.

Image volume extensions require PostgreSQL 18, Kubernetes 1.35 or newer (or 1.33+ with the `ImageVolume` feature gate), and containerd 2.1+ or CRI-O 1.31+.

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: autosecops-postgres
  namespace: autosecops
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:18-minimal-trixie
  storage:
    size: 50Gi
  bootstrap:
    initdb:
      database: autosecops
      owner: autosecops
  postgresql:
    extensions:
      - name: pgvector
        image:
          reference: ghcr.io/cloudnative-pg/pgvector:0.8.7-18-trixie
---
apiVersion: postgresql.cnpg.io/v1
kind: Database
metadata:
  name: autosecops-postgres-autosecops
  namespace: autosecops
spec:
  name: autosecops
  owner: autosecops
  cluster:
    name: autosecops-postgres
  extensions:
    - name: vector
      schema: public
```

The pgvector image tag must match the cluster's PostgreSQL major version and OS (`18-trixie` above). Point the chart at the read-write service and the `-app` Secret that CloudNativePG generates, which already has `username` and `password` keys:

```yaml
externalPostgres:
  host: "autosecops-postgres-rw.autosecops.svc"
  database: autosecops
  sslMode: require
  auth:
    existingSecret: autosecops-postgres-app
```

### Redis

```yaml
externalRedis:
  auth:
    existingSecret: autosecops-redis  # key: url
```

Use `rediss://` for TLS. Without a password, set `externalRedis.url` instead.

### S3

```yaml
externalS3:
  endpoint: ""            # blank for AWS S3
  region: us-west-2
  cspConnectSrcOrigins: "https://<attachments-bucket>.s3.us-west-2.amazonaws.com"
  auth:
    existingSecret: ""    # blank to use IRSA or Workload Identity
```

For S3-compatible storage, set `endpoint`. To serve presigned downloads through your public hostname as Docker Compose does, set `caddyProxyUpstream` to the same endpoint; the chart then defaults `presignedUrlEndpoint` to `<publicApp>/s3`.

### Temporal

```yaml
externalTemporal:
  clusterUrl: "temporal-frontend.temporal.svc:7233"
  namespace: default
```

For Temporal Cloud, set `clusterUrl` to `<namespace>.<account>.tmprl.cloud:7233`, set `namespace`, and reference the API key Secret in `externalTemporal.auth.existingSecret`. Run your own Temporal with the [Temporal Helm charts](https://github.com/temporalio/helm-charts).

## Install

<Steps>
  <Step title="Create your values file">
    ```yaml
    urls:
      publicApp: "https://autosecops.example.com"

    secrets:
      existingSecret: autosecops-core

    autosecops:
      auth:
        types: oidc
        allowedDomains: example.com
        superadminEmail: admin@example.com

    externalPostgres:
      host: "autosecops-db.example.internal"
      database: autosecops
      auth:
        existingSecret: autosecops-postgres

    externalRedis:
      auth:
        existingSecret: autosecops-redis

    externalS3:
      region: us-west-2

    externalTemporal:
      clusterUrl: "temporal-frontend.temporal.svc:7233"

    ingress:
      enabled: true
      className: nginx
      host: autosecops.example.com
      tls:
        - hosts: [autosecops.example.com]
          secretName: autosecops-tls

    networkPolicy:
      caddyIngressFrom:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
    ```

    `autosecops.auth.allowedDomains` limits sign-up to your email domains; leave it blank only if every domain may register. `values.schema.json` validates the file, and the chart fails rendering when a required Secret reference or URL is missing.
  </Step>

  <Step title="Install the chart">
    ```bash
    helm upgrade --install autosecops ./deployments/helm/autosecops \
      --namespace autosecops \
      -f values.yaml \
      --wait --timeout 15m
    ```

    The migrations hook runs before any workload starts, so a failed migration stops the release before it changes running pods.
  </Step>
</Steps>

## Networking

The Ingress sends every path to Caddy, which applies the Docker Compose routing: `/api` to the API with the prefix stripped, `/mcp` and the MCP OAuth routes to MCP, optional `/s3` to blob storage, and everything else to the UI. Set `caddy.trustedProxyCidrs` to the ranges your ingress controller or load balancer connects from so client IPs in `X-Forwarded-For` are trusted.

To route without Caddy, set `caddy.enabled: false` and `ingress.enabled: false`, then configure your gateway to strip `/api` before forwarding to the `api` Service on port 8000.

## Security

- Every pod runs as UID/GID 1001 with `runAsNonRoot`, the `RuntimeDefault` seccomp profile, `allowPrivilegeEscalation: false`, and all capabilities dropped. Caddy keeps `NET_BIND_SERVICE` because its binary carries that file capability.
- `api`, `worker`, `agent-worker`, `mcp`, `ui`, `caddy`, and the migrations Job use a read-only root filesystem with `emptyDir` scratch mounts for `/tmp`, the home caches, and `/var/run/tracecat`. `executor`, `agent-executor`, and `litellm` keep a writable root filesystem because custom registry installs and the LiteLLM runtime config write into the image. Override `<component>.containerSecurityContext` to change this.
- Service account tokens are not mounted, and `enableServiceLinks` is off.

### Execution sandboxing

Both executors default to `direct`, which runs actions inside the executor process. For nsjail isolation, set:

```yaml
executor:
  backend: nsjail
agentExecutor:
  backend: nsjail
```

nsjail pods run as root with `privileged: true`, `SYS_ADMIN`, and unconfined seccomp and AppArmor profiles, and start through the sandbox bootstrap entrypoint. Label the namespace for the `privileged` Pod Security level, and cap per-pod processes with the kubelet `podPidsLimit`, which replaces the Docker Compose `pids_limit`. See [Security](/self-hosting/security) for the isolation tradeoffs.

## Tunnels

[Tunnels](/manage-platform/tunnels) need the `tunnels` Enterprise entitlement and gateway workloads that the `api` service creates through the Kubernetes API. This chart version does not deploy the tunnel RBAC, namespace, or admission policy, so `TRACECAT__TUNNEL_GATEWAY_BACKEND` stays `none`. Contact SingularityRD before you enable tunnels on Kubernetes.

## Development dependencies

For evaluation clusters, `devDependencies.enabled: true` runs single-replica PostgreSQL (with pgvector), Redis, MinIO, and Temporal inside the release and points every component at them. Credentials still come from your Secrets: `externalPostgres.auth.existingSecret` for PostgreSQL and Temporal, and `externalS3.auth.existingSecret` for the MinIO root user. Migrations then run as a regular Job, because the bundled database starts with the release.

```yaml
urls:
  publicApp: "http://localhost:8080"
secrets:
  existingSecret: autosecops-core
externalPostgres:
  auth:
    existingSecret: autosecops-postgres
externalS3:
  auth:
    existingSecret: autosecops-minio  # keys: accessKeyId, secretAccessKey
devDependencies:
  enabled: true
```

These services have no replication or backups. Do not use them in production.

## Access AutoSecOps

- UI: `https://<your-domain>`
- API docs: `https://<your-domain>/api/docs`
- MCP: `https://<your-domain>/mcp`

Without an Ingress, port-forward Caddy: `kubectl -n autosecops port-forward svc/autosecops-caddy 8080:80`.

## Upgrade

```bash
helm upgrade autosecops ./deployments/helm/autosecops \
  --namespace autosecops \
  -f values.yaml \
  --wait --timeout 15m
```

`image.tag` and `uiImage.tag` default to the chart `appVersion`. Set both to pin a release; keep them on the same version.

<Warning>
  Never change or lose `dbEncryptionKey`, `serviceKey`, `signingSecret`, or `userAuthSecret` between upgrades.
  Losing them makes encrypted credentials unrecoverable and invalidates existing webhook URLs.
</Warning>

## FAQ

<AccordionGroup>
  <Accordion title="Connecting an in-cluster LiteLLM, vLLM, or Ollama fails with 'Host is not allowed'">
    AutoSecOps rejects LLM provider and MCP endpoints that resolve to private addresses unless you allow them.
    Set `autosecops.outboundAllowedPrivateCidrs` to the service's cluster IP or CIDR, e.g. `"10.96.0.0/12"`, and upgrade the release.
    See [Private endpoints](/agents/llm-providers#private-endpoints).
  </Accordion>

  <Accordion title="How do I pass settings the chart does not expose?">
    Add plain values under `autosecops.env` (every backend component) or `<component>.env`, and Secret references under `autosecops.extraEnv` or `<component>.extraEnv` as Kubernetes `EnvVar` entries, for example `OIDC_CLIENT_SECRET` from a `secretKeyRef`.
  </Accordion>

  <Accordion title="Can I run the chart in an air-gapped cluster?">
    Yes. Mirror the AutoSecOps, UI, and Caddy images into your registry, override `image.repository`, `uiImage.repository`, and `caddy.image.repository`, and set `imagePullSecrets`. See [Air-gapped deployment](/self-hosting/air-gapped).
  </Accordion>
</AccordionGroup>
