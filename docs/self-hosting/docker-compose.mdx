## Extract configuration files

Every AutoSecOps image ships the Docker Compose install files in `/opt/autosecops/install`: `docker-compose.yml`, `docker-compose.sandbox.yml`, `Caddyfile`, `.env.example`, `env.sh`, `env-migration.sh`, and the `backup_compose.sh` and `restore_compose.sh` scripts described in [Backup and restore](/self-hosting/backup-restore).
Copy them out of the image version you deploy into an empty directory:

```bash
# 1. Pull the AutoSecOps image
docker pull ghcr.io/singularityrd/autosecops:1.0.0

# 2. Copy the install files out of the image without starting it
id=$(docker create ghcr.io/singularityrd/autosecops:1.0.0)
docker cp "$id":/opt/autosecops/install/. .
docker rm "$id"
```

AutoSecOps uses Caddy as a reverse proxy, configured by the extracted `Caddyfile`.

## Generate the .env file

```bash
chmod +x env.sh && ./env.sh
```

After running `env.sh`, you'll be prompted to input the following:

- Use production mode? Defaults to `y`. Production mode generates random PostgreSQL, Temporal PostgreSQL, and MinIO passwords. Answer `n` only on a local development machine, which keeps the well-known development passwords.
- Set `PUBLIC_APP_URL`. Defaults to `localhost`.
- Require PostgreSQL SSL mode? Defaults to `n`, because the bundled `postgres_db` container is reachable only on the internal Compose network. Use `require` or `verify-full` in `AUTOSECOPS__DB_SSLMODE` when you point `AUTOSECOPS__DB_URI` at an external database.
- Required field: Enter email address for the first user (superadmin).

Then set `AUTOSECOPS__AUTH_ALLOWED_DOMAINS` in `.env` to your organization's email domains, e.g. `example.com`. While it is blank, anyone who can reach the login page can sign up.

Verify the file before you start AutoSecOps. The check exits non-zero while any `change-me-` placeholder remains:

```bash
./env.sh --check
```

<Warning>
  Docker Compose defaults to the `direct` executor backend, which does not sandbox ordinary workflow actions.
  For supported action isolation, set `AUTOSECOPS__EXECUTOR_BACKEND=nsjail`, then start with the sandbox overlay described in [Security](/self-hosting/security#nsjail-sandbox-recommended-for-production).
  The legacy `ephemeral` value remains a compatibility alias for `nsjail`.
</Warning>

## Start AutoSecOps

For the direct backend, run the command below to start AutoSecOps and all related services.
Make sure your `docker-compose.yml` and generated `.env` files are in the same directory.

```bash
docker compose up
```

For nsjail, use the `docker-compose.sandbox.yml` you extracted beside `docker-compose.yml`; it comes from the same AutoSecOps release as your image. Start with both files so the overlay supplies the container permissions and cgroup bootstrap:

```bash
AUTOSECOPS__EXECUTOR_BACKEND=nsjail docker compose \
  -f docker-compose.yml -f docker-compose.sandbox.yml up -d
```

If you build locally with `docker-compose.local.yml`, substitute that file for `docker-compose.yml` in the command.

## Access AutoSecOps

Once deployed, access your instance at:
- UI: `http://localhost:${PUBLIC_APP_PORT}`
- API docs: `http://localhost:${PUBLIC_APP_PORT}/api/docs`
- MCP: `http://localhost:${PUBLIC_APP_PORT}/mcp`

<Warning>
  Plain HTTP is fine for local development on `localhost`, but do not expose an HTTP-only deployment to a public domain.
  Modern browsers upgrade requests to a public hostname to HTTPS, so the UI fails with `ERR_CONNECTION_REFUSED` even while `curl` over HTTP still works.
  Enable TLS before going to production. See [TLS and certificates](/self-hosting/tls).
</Warning>

## Updating AutoSecOps

<Warning>
  Be careful when updating AutoSecOps.
  Do not accidentally overwrite or lose your existing `AUTOSECOPS__SERVICE_KEY`, `AUTOSECOPS__SIGNING_SECRET`, `AUTOSECOPS__DB_ENCRYPTION_KEY`, and `USER_AUTH_SECRET` secrets.
  Losing these secrets will break your credentials and webhooks.
</Warning>

Read the release notes and take a backup first: run `./backup_compose.sh -o /var/backups/autosecops`, as described in [Backup and restore](/self-hosting/backup-restore). See [Updating AutoSecOps](/self-hosting/updating) for watching migrations, post-upgrade checks, and rollback.

Replace `<version>` with the AutoSecOps version you are upgrading to. If `docker pull` fails with `denied` or `unauthorized`, log in again as described in [Registry access](#registry-access). The commands extract the new install files into a separate directory first, so nothing in your deployment directory changes until you copy a file over.

```bash
# 1. Pull the new image and extract its install files into ./autosecops-<version>
docker pull ghcr.io/singularityrd/autosecops:<version>
mkdir -p autosecops-<version>
id=$(docker create ghcr.io/singularityrd/autosecops:<version>)
docker cp "$id":/opt/autosecops/install/. autosecops-<version>/
docker rm "$id"

# 2. Copy the env migration script and env template, then update your existing .env
cp autosecops-<version>/env-migration.sh autosecops-<version>/.env.example .
chmod +x env-migration.sh && ./env-migration.sh

# 3. Back up and replace the Docker Compose files
cp docker-compose.yml docker-compose.yml.bak
cp autosecops-<version>/docker-compose.yml autosecops-<version>/docker-compose.sandbox.yml .
cp autosecops-<version>/backup_compose.sh autosecops-<version>/restore_compose.sh .

# 4. Back up and replace the Caddyfile
cp Caddyfile Caddyfile.bak
cp autosecops-<version>/Caddyfile .

# 5. Restart AutoSecOps with the updated configuration
docker compose up -d
```

If you pinned `AUTOSECOPS__IMAGE_TAG` in `.env`, set it to the new version before step 5.

The `redis` service runs Valkey and stores its data in the `valkey-data` volume. Valkey cannot read data files written by Redis 7.4 or later, so when you upgrade from a release that ran `redis:7-alpine`, the service starts with an empty store and leaves the old `redis-data` volume untouched. Let running workflows and agent sessions finish before you upgrade, because their in-flight stream data stays in the old volume. Once the stack is healthy, you can delete the old volume with `docker volume rm <project>_redis-data`.

The `temporal_postgres_db` service runs PostgreSQL 16. If your `temporal-db` volume holds PostgreSQL 13 data from an earlier release, the service stops with a message until you [upgrade the Temporal database](/self-hosting/updating#upgrade-the-temporal-database) or pin `TEMPORAL__POSTGRES_IMAGE=postgres:13` in `.env`.

The migration script creates a backup of your existing `.env` before rewriting it.
After the stack starts, verify that your containers are healthy and that you can sign in successfully.

## Scaling

Docker Compose runs all services on a single host.
These are recommended minimums for different workload sizes.

| Resource | Small | Standard | Production |
| :------- | :---- | :------- | :--------- |
| CPU | 8 cores | 16 cores | 32+ cores |
| RAM | 16 GB | 32 GB | 64+ GB |
| Storage | 20 GB SSD | 50 GB SSD | 100+ GB SSD |
| Docker | 26.0.0+ | 26.0.0+ | 26.0.0+ |
| Workflow starts/sec | ~5 | ~15 | ~40 |
| Concurrent seats | 1-10 | 10-50 | 50+ |
| Concurrent agents/sec | 1-2 | 5-10 | 10+ |

- Small: Development, testing, small teams (1-10 users)
- Standard: Mid-size teams (10-50 users), moderate workflow execution
- Production: Large teams (50+ users), high throughput

Memory is typically the constraining factor.
Workflow throughput is lower than dedicated Kubernetes deployments where services have guaranteed resources and can scale independently.

To size executor replicas, concurrency settings, and PostgreSQL connections for a target of up to 256 actions per second, see [Scaling action throughput](/self-hosting/scaling).

For production workloads that exceed single-host capacity, consider [converting to Docker Swarm](#convert-to-docker-swarm) or deploying on Kubernetes.

## Convert to Docker Swarm

Docker Swarm lets you scale individual services with resource limits and replicas across one or more nodes.

### Service resource recommendations

| Service | CPU (cores) | Memory | Replicas |
| :------ | ----------: | -----: | -------: |
| caddy | 0.25 | 256 Mi | 1 |
| api | 2 | 4 Gi | 2 |
| worker | 2 | 2 Gi | 4 |
| executor | 4 | 8 Gi | 4 |
| agent-worker | 2 | 2 Gi | 2 |
| agent-executor | 4 | 16 Gi | 2 |
| ui | 0.5 | 1 Gi | 2 |
| mcp | 1 | 1 Gi | 1 |
| postgres_db | 2 | 4 Gi | 1 |
| temporal | 4 | 8 Gi | 1 |
| temporal_postgres_db | 2 | 4 Gi | 1 |
| redis | 0.5 | 1 Gi | 1 |
| minio | 0.5 | 1 Gi | 1 |
| Total | ~25 | ~52 Gi | 23 |

<Info>
  Stateful services (`postgres_db`, `temporal_postgres_db`, `minio`, `redis`) must remain at 1 replica.
  Scaling these requires external managed services (e.g., RDS, ElastiCache) or specialized clustering.
</Info>

### Deploy with Docker Swarm

1. Initialize Swarm:

```bash
docker swarm init
```

2. Add `deploy` configuration to each service in your `docker-compose.yml`. For example, for the `api` service:

```yaml
services:
  api:
    # ... existing configuration ...
    deploy:
      replicas: 2
      resources:
        limits:
          cpus: "2"
          memory: 4G
        reservations:
          cpus: "2"
          memory: 4G
```

3. Deploy the stack:

```bash
docker stack deploy -c docker-compose.yml autosecops
```

4. Verify services are running:

```bash
docker stack services autosecops
```

## FAQ

For an overview of all services and networking, see [Architecture](/self-hosting/architecture).

<AccordionGroup>
  <Accordion title="Does AutoSecOps support Windows?">
    Yes but don't forget to set `PUBLIC_APP_URL` to `127.0.0.1` instead of `localhost` in your `.env` file.
  </Accordion>

  <Accordion title="Does AutoSecOps support WSL?">
    Yes but you'll need to set `PUBLIC_APP_URL` to the WSL IP address instead of `localhost`.
    Run `ip addr` to find your WSL IP address (usually 172.x.x.x).
  </Accordion>

  <Accordion title="Connecting LiteLLM, vLLM, or Ollama fails with 'Host is not allowed'">
    AutoSecOps rejects LLM provider and MCP endpoints that resolve to private addresses unless you allow them.
    Set `AUTOSECOPS__OUTBOUND_ALLOWED_PRIVATE_CIDRS` in your `.env` file to the gateway's IP or CIDR, e.g. `AUTOSECOPS__OUTBOUND_ALLOWED_PRIVATE_CIDRS=10.0.12.34/32`, then run `docker compose up -d` to restart the services.
    See [Private endpoints](/agents/llm-providers#private-endpoints).
  </Accordion>

  <Accordion title="I can see the landing page but not the login page">
    This suggests that the AutoSecOps UI is healthy but is unable to communicate with the AutoSecOps API.

    - Check that the `api` service is healthy
    - Check that this is not a CORS issue (see next FAQ)
    - Check that you changed `PUBLIC_APP_URL` and `PUBLIC_APP_PORT` to the correct address
    - Check the Chrome developer console for any errors
  </Accordion>

  <Accordion title="What is the CORS issue?">
    You must configure `PUBLIC_APP_URL` and `PUBLIC_API_URL` to the same domain that your browser is accessing the AutoSecOps UI from.
    AutoSecOps strictly enforces CORS to prevent XSS attacks.

    This error occurs when your browser cannot connect to AutoSecOps API via `PUBLIC_APP_URL`.
    Please check the following:

    - Do not set `PUBLIC_APP_URL` to `0.0.0.0`. Browsers cannot connect to this address. Use `localhost`, `127.0.0.1`, or your machine's actual IP address instead.
    - WSL users: Do not use `127.0.0.1`. Run `ip addr` to find your WSL IP address (usually `172.x.x.x`) and use that instead.
    - If your frontend is running on a different machine than the API, set `NEXT_PUBLIC_API_URL` to an address your browser can reach.
    - Run `docker compose ps` to verify all services are running.
    - Check the temporal service is healthy. Worker connectivity issues can sometimes affect login.
    - View container logs: `docker compose logs api` and `docker compose logs temporal`.
    - Check firewall and port forwarding if using a reverse proxy.

    For example, if you've deployed AutoSecOps into a VM and exposed it to your browser as `https://my-autosecops-instance.com`,
    you must set:
    - `PUBLIC_APP_URL` to `https://my-autosecops-instance.com`
    - `PUBLIC_API_URL` to `https://my-autosecops-instance.com/api`
  </Accordion>

  <Accordion title="What should PUBLIC_APP_URL and PUBLIC_API_URL be, and how do I fix login or CORS issues?">
    Set both values to the exact browser-reachable URLs for your deployment, including the scheme:

    - Local example:
      - `PUBLIC_APP_URL=http://localhost:8000`
      - `PUBLIC_API_URL=http://localhost:8000/api`
    - Reverse proxy or public domain example:
      - `PUBLIC_APP_URL=https://autosecops.example.com`
      - `PUBLIC_API_URL=https://autosecops.example.com/api`

    Use full URLs once.
    Do not prepend `http://` or `https://` twice, and do not use addresses that only work inside Docker such as `0.0.0.0` or internal container hostnames.

    If sign-in still fails:

    - Verify that the domain in your browser exactly matches `PUBLIC_APP_URL`.
    - Verify that `PUBLIC_API_URL` is the same origin plus `/api`.
    - Run `docker compose ps` and check that `api`, `worker`, and `temporal` are healthy.
    - Review `docker compose logs api` for startup, auth, or CORS errors.
  </Accordion>

  <Accordion title="I'm seeing 'No hosts available' errors from Temporal">
    Undersized Temporal clusters cause `No hosts available` errors and workflow execution failures.
    Ensure the Temporal server has at least 4 CPU cores and 8 GB of memory.

    Temporal also requires a well-provisioned PostgreSQL backend for adequate query throughput.
    The bundled `temporal_postgres_db` container is suitable for development and small deployments only.
    For production workloads, use a managed PostgreSQL instance (e.g., Amazon Aurora Serverless) for better QPS and reliability.
  </Accordion>

  <Accordion title="My browser shows ERR_CONNECTION_REFUSED but curl over HTTP works">
    Your deployment is serving plain HTTP, but the browser is upgrading the request to HTTPS.
    See [Browsers force HTTPS](/self-hosting/tls#browsers-force-https).
  </Accordion>

  <Accordion title="How do I configure SSL for production?">
    See [TLS and certificates](/self-hosting/tls) for automatic Let's Encrypt setup with Caddy, custom certificates, and trusting internal CAs for outbound connections.
  </Accordion>
</AccordionGroup>
