title: Updating AutoSecOps
description: Learn how to safely update versions and run data migrations.

Updates and data migrations can be tricky business. Follow the steps below carefully.

<Warning>
  If you want to migrate secrets, please make sure to save your database
  encryption / decryption Fernet key. You can find this key in your `.env` file
  assigned to the environment variable: `AUTOSECOPS__DB_ENCRYPTION_KEY`.
</Warning>

## Docker Compose

<Steps>
  <Step title="Extract the install files from the new image">
    Every AutoSecOps image ships its Docker Compose install files in
    `/opt/autosecops/install`. Pull the version you are upgrading to and copy
    them into a separate directory, so nothing in your deployment directory
    changes yet. If `docker pull` fails with `denied` or `unauthorized`, log in
    to GHCR again as described in [Registry access](/self-hosting/docker-compose#registry-access).

    ```
    docker pull ghcr.io/singularityrd/autosecops:1.0.0
    mkdir -p autosecops-1.0.0
    id=$(docker create ghcr.io/singularityrd/autosecops:1.0.0)
    docker cp "$id":/opt/autosecops/install/. autosecops-1.0.0/
    docker rm "$id"
    ```

  </Step>
  <Step title="Execute environment variables migration">
    Copy the environment variables migration script `env-migration.sh` and
    template `.env.example` into your deployment directory, then run the
    script to update your existing `.env` file with any new or changed
    variables.

    ```
    cp autosecops-1.0.0/env-migration.sh autosecops-1.0.0/.env.example .
    chmod +x env-migration.sh && ./env-migration.sh
    ```

  </Step>
  <Step title="Update Docker Compose configuration">
    <Warning>
      If you modified `docker-compose.yml` or `Caddyfile`, make copies before
      you continue. The commands below overwrite both files and discard your
      local changes.
    </Warning>

    Replace the Docker Compose files with the ones from the new image.

    ```
    # Back up your existing docker-compose.yml first; the copy below overwrites it
    cp docker-compose.yml docker-compose.yml.bak
    cp autosecops-1.0.0/docker-compose.yml autosecops-1.0.0/docker-compose.sandbox.yml .
    ```
  </Step>
  <Step title="Update Caddyfile">
    Replace the Caddyfile with the one from the new image.

    ```
    # Back up your existing Caddyfile first; the copy below overwrites it
    cp Caddyfile Caddyfile.bak
    cp autosecops-1.0.0/Caddyfile .
    ```
  </Step>
  <Step title="Restart AutoSecOps">
    Run `docker compose up -d` using the new Docker Compose and `.env` files.
  </Step>
</Steps>

## Update Integrations

Integrations are not automatically updated when you update the AutoSecOps version.
You will need to manually sync the `autosecops_registry` repository from the **Registry** page:

![Sync registry](/img/custom-actions/sync-from-remote.png)

## Terraform Deployments

AWS Fargate deployments of AutoSecOps are configured using Terraform.
To update AutoSecOps, extract the Terraform stack from the new image version, update the Terraform variable `autosecops_image_tag` to that version, and run `terraform apply`.
See [Updating AutoSecOps on Fargate](/self-hosting/aws-fargate#updating-autosecops) for the full steps.

## Data Migration

Data migrations are non-trivial operations.
We recommend backing up your database before running migrations, especially in a production environment.

<Info>
If the API service fails to spin up due to a data migration error, do not worry.
Your data is still intact. Make sure you backup the core AutoSecOps database:

- For Docker Compose and AWS EC2 deployments, this would be the `core-db` volume in AutoSecOps's Docker stack.
- For AWS ECS Fargate deployments, backups are created automatically as part of the RDS postgres service. Just run `terraform apply` with `var.restore_from_backup` set to `true` to restore the latest RDS snapshot.

If you need live migration support, contact [info@singularityrd.com](mailto:info@singularityrd.com).
</Info>
