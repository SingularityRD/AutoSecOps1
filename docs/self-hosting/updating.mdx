AutoSecOps versions follow semantic versioning. Self-hosted deployments run stable versions only, `MAJOR.MINOR.PATCH`:

| Release | Contains | Database migrations | Image-only rollback |
| --- | --- | --- | --- |
| Patch, e.g. `1.4.2` to `1.4.3` | Fixes cherry-picked onto the release train, including [security patches](/self-hosting/security-patches) | Never | Yes, to an earlier patch of the same `1.4` train |
| Minor, e.g. `1.4.3` to `1.5.0` | New features and fixes | Often | No. Restore the pre-upgrade backup |
| Major, e.g. `1.5.0` to `2.0.0` | Changes that need manual steps, listed in the release notes | Often | No. Restore the pre-upgrade backup |

You can upgrade across several versions at once. The migrations apply every intermediate revision in order. Read the release notes of every version you skip.

SingularityRD supports the latest two minor release trains, each for 12 months after its release; see the [support policy](/self-hosting/support-policy). The [changelog](/self-hosting/changelog) lists the upgrade notes of every release.

## Before you upgrade

1. Read the [changelog](/self-hosting/changelog) and the release notes for every version between yours and the target. Look for upgrade notes, new required settings, and breaking changes.
2. Note the version you run now. `GET /api/info` returns it in `version`:

   ```bash
   curl -fsS https://autosecops.example.com/api/info
   ```

3. Back up the database, object storage, and secrets. See [Backup and restore](/self-hosting/backup-restore). On Docker Compose:

   ```bash
   ./backup_compose.sh -o /var/backups/autosecops
   ```

4. Plan for downtime. On Docker Compose and Fargate, the API stays down until the migrations finish. Most migrations take seconds; release notes call out migrations that rewrite large tables.
5. On a multi-tenant deployment, check that `AUTOSECOPS__LICENSE_KEY` is set on every service and grants `multi_tenant`. With `AUTOSECOPS__EE_MULTI_TENANT=true`, more than one organization, and no such license, the `api` service refuses to start. See [Multi-tenant deployments](/self-hosting/license#multi-tenant-deployments).

<Warning>
  Keep `AUTOSECOPS__DB_ENCRYPTION_KEY`, `AUTOSECOPS__SERVICE_KEY`, `AUTOSECOPS__SIGNING_SECRET`, and `USER_AUTH_SECRET` unchanged across the upgrade. A different `AUTOSECOPS__DB_ENCRYPTION_KEY` makes every stored credential unrecoverable.
</Warning>

## Docker Compose

<Steps>
  <Step title="Extract the install files from the new image">
    Every AutoSecOps image ships its Docker Compose install files in
    `/opt/autosecops/install`. Pull the version you are upgrading to and copy
    them into a separate directory, so nothing in your deployment directory
    changes yet. If `docker pull` fails with `denied` or `unauthorized`, log in
    to GHCR again as described in [Registry access](/self-hosting/docker-compose#registry-access).

    ```bash
    docker pull ghcr.io/singularityrd/autosecops:<version>
    mkdir -p autosecops-<version>
    id=$(docker create ghcr.io/singularityrd/autosecops:<version>)
    docker cp "$id":/opt/autosecops/install/. autosecops-<version>/
    docker rm "$id"
    ```
  </Step>
  <Step title="Migrate the environment variables">
    Copy the environment variables migration script `env-migration.sh`, the
    `env.sh` helper, and the template `.env.example` into your deployment
    directory, then run the script. It backs up your `.env`, adds any new or
    changed variables, and generates the database runtime role password and
    the [Redis password](#redis-password) when `.env` has none.
    `./env.sh --check` then confirms no placeholder remains.

    ```bash
    cp autosecops-<version>/env-migration.sh autosecops-<version>/env.sh autosecops-<version>/.env.example .
    chmod +x env-migration.sh env.sh && ./env-migration.sh
    ./env.sh --check
    ```
  </Step>
  <Step title="Replace the Compose files, Caddyfile, and scripts">
    The copies below overwrite your files. If you changed `docker-compose.yml`
    or `Caddyfile`, carry your changes over from the `.bak` copies.

    ```bash
    cp docker-compose.yml docker-compose.yml.bak
    cp Caddyfile Caddyfile.bak
    cp autosecops-<version>/docker-compose.yml autosecops-<version>/docker-compose.sandbox.yml .
    cp autosecops-<version>/Caddyfile .
    cp autosecops-<version>/backup_compose.sh autosecops-<version>/restore_compose.sh autosecops-<version>/support_bundle.sh .
    ```

    If you pinned `AUTOSECOPS__IMAGE_TAG` in `.env`, set it to `<version>`.
  </Step>
  <Step title="Check your override file">
    If you have a `docker-compose.override.yml`, check it against
    [Resource limits and log rotation](#resource-limits-and-log-rotation)
    before you restart. A `mem_limit`, `cpus`, or `pids_limit` setting there
    stops `docker compose up`.
  </Step>
  <Step title="Pull the images and restart">
    ```bash
    docker compose pull
    docker compose up -d
    ```

    Add `-f docker-compose.sandbox.yml` to both commands if you run the nsjail backend.
    The `migrations` service creates the runtime role before the other
    services start. Then [verify isolation](/self-hosting/security#verify-isolation).
  </Step>
</Steps>

## Redis password

The bundled Redis (Valkey) requires a password from the release that adds `REDIS_PASSWORD` to `.env.example`. Earlier installs accepted unauthenticated connections from every container on the `core` network.

- `./env-migration.sh` sets `REDIS_PASSWORD` in `.env`. If you skipped it, run `./env.sh --upgrade`: it backs up `.env` and adds the password, and running it again changes nothing.
- Both reuse the password from `REDIS_URL` when it has one, so installs that added a password to `REDIS_URL` by hand keep it. Otherwise they generate one. Remove any `redis` `command` override with `--requirepass` from `docker-compose.override.yml`: the `redis` service now sets the password itself.
- Without `REDIS_PASSWORD`, `docker compose up` stops with `REDIS_PASSWORD is not set. Run ./env.sh --upgrade`. With the `.env.example` placeholder, the `redis` container exits with the same instruction.
- Redis keeps its data: the password does not change the `valkey-data` volume. `docker compose up -d` recreates `redis` and every service with the new setting.
- If `REDIS_URL` points to an external Redis without a password, both scripts also add `REDIS_CLIENT_PASSWORD=` (empty) to `.env` and print a warning. The services then keep connecting to that Redis without a password, as before the upgrade. Without that line they would send `REDIS_PASSWORD`, which a Redis without authentication rejects. Prefer enabling authentication on that Redis: put its password in `REDIS_URL`, which takes precedence, and remove `REDIS_CLIENT_PASSWORD`.

## Database runtime role password

`./env-migration.sh` and `./env.sh --upgrade` generate `AUTOSECOPS__DB_RUNTIME_PASSWORD` when `.env` has none or still has the `.env.example` placeholder. On the next start, the `migrations` service creates the `autosecops_app` role with it, or resets the role's password, and the services connect as that role, so tenant row-level security applies. An `.env` that sets it to an empty value on purpose keeps it empty: AutoSecOps then runs as the owner role, logs a warning, and row-level security stays inactive.

## Resource limits and log rotation

The release that adds `REDIS_PASSWORD` also adds [memory limits](/self-hosting/docker-compose#resource-limits) and [log rotation](/self-hosting/docker-compose#log-rotation) to every Compose service. `docker compose up -d` recreates the containers, which applies both. Check these before you restart:

- A service that used more memory than its new limit before the upgrade restarts with `OOMKilled: true` in `docker inspect`; raise its `AUTOSECOPS__<SERVICE>_MEMORY_LIMIT` in `.env`. Redis now refuses writes with `OOM command not allowed` at 75% of its limit instead of growing without bound; raise `AUTOSECOPS__REDIS_MEMORY_LIMIT` if its dataset is larger.
- The limits live under `deploy.resources.limits`. A `deploy.resources.limits` block in `docker-compose.override.yml`, as earlier versions of [Scaling action throughput](/self-hosting/scaling) suggested, keeps working: Compose merges it over the defaults. A `mem_limit`, `cpus`, or `pids_limit` setting on the same service stops `docker compose up` with `can't set distinct values on 'mem_limit' and 'deploy.resources.limits.memory'`. Remove it and set the value through `AUTOSECOPS__<SERVICE>_MEMORY_LIMIT` and `AUTOSECOPS__<SERVICE>_CPU_LIMIT` in `.env`, or through `deploy.resources.limits`.
- Every service now sets the `json-file` log driver, which overrides `log-driver` in the Docker daemon's `daemon.json`. If the daemon ships container logs to journald, syslog, a collector, or a SIEM, add the [daemon log driver override](/self-hosting/docker-compose#log-rotation) before you restart, or those logs stop reaching it.

On Kubernetes, the chart now refuses an inline `externalRedis.auth.url` without a password. Add the password to the URL, or set `externalRedis.auth.allowUnauthenticated: true` to keep an unauthenticated Redis.

## Upgrade the Temporal database

The Docker Compose `temporal_postgres_db` service runs PostgreSQL 16 and the `temporal` service runs Temporal 1.29.1. Earlier releases ran PostgreSQL 13 and Temporal 1.27.1. To check whether your install needs this upgrade, look at the Compose file you replaced:

```bash
grep -n 'postgres:13' docker-compose.yml.bak
```

PostgreSQL 16 cannot open a data directory that PostgreSQL 13 wrote. When it finds one in the `temporal-db` volume, `temporal_postgres_db` exits without touching the volume and logs:

```text
temporal_postgres_db: the temporal-db volume holds PostgreSQL 13 data, but this image runs PostgreSQL 16.
```

Temporal, and every service that depends on it, stays down until you either upgrade the database or pin the old version.

To keep running PostgreSQL 13 for now, add `TEMPORAL__POSTGRES_IMAGE=postgres:13` to `.env` and run `docker compose up -d`. `env-migration.sh` keeps this line. PostgreSQL 13 no longer receives security fixes, so plan the upgrade below.

The upgrade dumps the Temporal databases from PostgreSQL 13, moves the old volume aside, and restores the dumps into PostgreSQL 16 on a fresh volume. It keeps workflow history, schedules, and timers. Run it from your deployment directory after the [Docker Compose](#docker-compose) steps, and add `-f docker-compose.sandbox.yml` to the `docker compose` commands if you run the nsjail backend.

<Steps>
  <Step title="Stop the stack and start the old database">
    ```bash
    docker compose down
    TEMPORAL__POSTGRES_IMAGE=postgres:13 docker compose up -d temporal_postgres_db
    docker compose exec temporal_postgres_db sh -c 'until pg_isready -q -h 127.0.0.1 -U "$POSTGRES_USER"; do sleep 1; done'
    ```

    `docker compose down` keeps volumes. Do not add `-v`.
  </Step>
  <Step title="Dump the Temporal databases">
    List the databases. Expect `temporal` and `temporal_visibility`; dump any other database it lists besides `postgres` too.

    ```bash
    docker compose exec -T temporal_postgres_db sh -c 'PGUSER="$POSTGRES_USER" exec psql -XAtq -d postgres -c "select datname from pg_database where not datistemplate"'
    ```

    ```bash
    mkdir -p temporal-pg13-dump
    for db in temporal temporal_visibility; do
      docker compose exec -T temporal_postgres_db sh -c 'PGUSER="$POSTGRES_USER" exec pg_dump -Fc -d "$1"' sh "$db" > "temporal-pg13-dump/$db.dump"
    done
    ls -l temporal-pg13-dump
    ```

    Both files must be larger than zero bytes before you continue.
  </Step>
  <Step title="Move the PostgreSQL 13 volume aside">
    Find the volume name. Compose prefixes it with the project name, which defaults to the deployment directory name:

    ```bash
    docker compose rm -sf temporal_postgres_db
    docker volume ls --filter name=temporal-db
    ```

    Copy it to a rollback volume, then remove the original so PostgreSQL 16 starts on a fresh one. Replace `<project>` with your project name. The copy needs as much free disk as the volume uses.

    ```bash
    docker volume create <project>_temporal-db-pg13
    docker run --rm -v <project>_temporal-db:/from:ro -v <project>_temporal-db-pg13:/to postgres:13 cp -a /from/. /to/
    docker volume rm <project>_temporal-db
    ```
  </Step>
  <Step title="Start PostgreSQL 16 and restore">
    ```bash
    docker compose up -d temporal_postgres_db
    docker compose exec temporal_postgres_db sh -c 'until pg_isready -q -h 127.0.0.1 -U "$POSTGRES_USER"; do sleep 1; done'
    for db in temporal temporal_visibility; do
      docker compose exec -T temporal_postgres_db sh -c 'PGUSER="$POSTGRES_USER" exec psql -XAtq -v ON_ERROR_STOP=1 -d template1 -c "DROP DATABASE IF EXISTS \"$1\"" -c "CREATE DATABASE \"$1\" TEMPLATE template0"' sh "$db"
      docker compose exec -T temporal_postgres_db sh -c 'PGUSER="$POSTGRES_USER" exec pg_restore --no-owner --exit-on-error --single-transaction -d "$1"' sh "$db" < "temporal-pg13-dump/$db.dump"
    done
    ```

    `DROP DATABASE` only removes the empty database that PostgreSQL 16 created on first start.
  </Step>
  <Step title="Step Temporal through 1.28">
    Temporal supports upgrades one minor version at a time. Run 1.28 once so it applies its schema changes, then start the full stack on 1.29.1:

    ```bash
    TEMPORAL__VERSION=1.28.4 docker compose up -d temporal
    docker compose ps temporal   # wait for "healthy"
    docker compose up -d
    ```
  </Step>
  <Step title="Check and clean up">
    Open the Temporal UI or run `docker compose exec temporal tctl --address temporal:7233 --namespace default workflow list`, and check that your schedules still fire, as in [Check the upgrade](#check-the-upgrade). Then delete the rollback copy and the dumps:

    ```bash
    docker volume rm <project>_temporal-db-pg13
    rm -r temporal-pg13-dump
    ```
  </Step>
</Steps>

To roll back before you delete the copy, stop the stack, copy `<project>_temporal-db-pg13` back into an empty `<project>_temporal-db` volume with the same `docker run ... cp -a` command, and start with `TEMPORAL__POSTGRES_IMAGE=postgres:13` and `TEMPORAL__VERSION=1.27.1` in `.env`.

Fargate deployments keep Temporal on the RDS instance `temporal-database` and already run Temporal 1.29.1. The Helm chart connects to your own Temporal server; run Temporal 1.29 or later there too.

## Watch the migrations

Every deployment target runs `alembic upgrade head` from the new image before the API starts. Only one migration run proceeds at a time: others wait on a PostgreSQL advisory lock.

| Target | Where migrations run | Follow them |
| --- | --- | --- |
| Docker Compose | The `migrations` service. `api` and the workers start after it exits with code 0 | `docker compose logs -f migrations` |
| Kubernetes | The `autosecops-migrations` Job, a `pre-upgrade` hook. Pods roll after it succeeds | `kubectl -n autosecops logs job/autosecops-migrations -f` |
| AWS Fargate | The migrations init container in each API task. The API container starts after it succeeds | `aws logs tail /ecs/autosecops --log-stream-name-prefix api-migrations --follow` |

Each applied revision logs one `Running upgrade <from> -> <to>` line. To read the revision the database is at:

```bash
docker compose exec postgres_db sh -c 'psql -U "$POSTGRES_USER" -d postgres -XAt -c "select version_num from alembic_version"'
```

A failed migration leaves the API stopped and logs the error. PostgreSQL rolls back the failed revision, `alembic_version` keeps the last revision that committed, and the next run continues from there. Send the migration log to [info@singularityrd.com](mailto:info@singularityrd.com), or roll back as described below.

### Session and invitation token hashing

From the release that adds revision `3f7a9c2d5b81`, AutoSecOps stores new session tokens and invitation tokens as SHA-256 digests. The migration only adds columns: it rewrites no existing rows, takes its table locks only briefly, and leaves existing sessions and emailed invitation links working. Tokens issued before the upgrade stay stored as before until they expire or a later release hashes them.

While the rollout still runs the previous version next to the new one:

- Sessions created on an upgraded pod or task are not recognized by one still on the previous version. Users routed there sign in again.
- Do not create invitations until every pod or task runs the new version. The previous version can email or copy an unusable link for an invitation created on the new one. Resend any invitation created during the rollout once it finishes.
- To avoid both effects, scale `api` and the workers to zero before the migration runs, then start the new version.

To roll back, restore the pre-upgrade backup. If you run `alembic downgrade` instead, it signs out every user who signed in after the upgrade and revokes every pending invitation created after the upgrade, because the previous version cannot use a stored digest. The migration log states how many of each. Invite those users again after the downgrade. Sessions and invitations created before the upgrade keep working.

## Check the upgrade

Run these checks right after every upgrade:

1. `docker compose ps -a` shows `migrations` as `Exited (0)` and every other service as `running` or `healthy`. On Kubernetes, the migrations Job is `Complete` and every pod is `Ready`.
2. `curl -fsS https://autosecops.example.com/api/health` returns `{"status":"ok"}`, and `/api/info` returns the new `version`.
3. You can sign in through your identity provider.
4. A workflow that uses a stored credential runs to completion. A webhook-triggered workflow accepts a test event.
5. A case with an attachment opens and the attachment downloads.
6. Scheduled workflows fire on their next interval.

### Worker health checks

From this release, the Temporal workers report health. Docker Compose shows `worker`, `background-worker`, `executor`, `agent-worker`, and `agent-executor` as `healthy` once they poll Temporal, and the Helm chart adds exec startup, liveness, and readiness probes to their pods, so `helm upgrade` waits for new worker pods to become ready.
A worker that stays `unhealthy` or not ready cannot reach Temporal; check its logs.
The chart's default worker probes live in the new `workerProbes` value. A probe you already set on a worker component (for example `worker.readinessProbe`) replaces the matching default; it is never merged with it. If you mounted a volume at `/var/run/autosecops` through `extraVolumeMounts`, remove it: the chart now mounts an in-memory `emptyDir` there for the health files, and a duplicate mount path fails the upgrade.
On AWS Fargate, worker tasks get an ECS container health check, and the new `metrics_enabled` and `metrics_scraper_security_group_ids` module variables turn on metrics. See [Monitoring](/self-hosting/monitoring).

## Agent workers during a rolling upgrade

Kubernetes and Fargate replace agent worker replicas one at a time, so for a few minutes old and new agent workers share the same Temporal task queue. A new release can add an agent activity, such as the [model lookup by name](/agents/custom-llm-providers#credentials) for agent configurations without a `catalog_id`. When an old worker receives that activity, it fails the attempt as not registered, and AutoSecOps retries it for up to 10 minutes until an upgraded worker takes it.

- Let the agent worker rollout finish within 10 minutes. `kubectl -n autosecops rollout status deployment/autosecops-agent-worker` reports progress on Kubernetes.
- An agent run whose activity is not picked up within 10 minutes fails with an activity timeout. Rerun it after the rollout completes.

## Agent runtime hardening

From the release that hardens the agent runtime, three agent behaviors change:

- The `agent-executor` worker marks itself non-dumpable at startup, as the executor worker already does. It writes no core dumps, and attaching `py-spy` or `gdb` to it needs `CAP_SYS_PTRACE`.
- Tool results and tool errors that the trusted MCP proxy returns for remote MCP integrations show `***` in place of that integration's own credentials. AutoSecOps masks the values of credential headers such as `Authorization`, `Cookie`, and `X-Api-Key`, each word of 8 characters or more in a value such as `Bearer <token>`, and the password in any header URL. Other header values, such as `Accept` or a base URL, stay as they are. Stdio MCP servers that the agent runtime starts itself, which includes every stdio server with the built-in runner, return results straight to the agent, so AutoSecOps does not mask their output. Treat a stdio server that can echo its environment as able to reveal those credentials to the model and the transcript.
- On the `direct` backend, stdio MCP connection probes no longer use the worker's home directory, and resolve the server command on the same `PATH` as agent runs, `/usr/local/bin:/usr/bin:/bin`. `python` and `python3` in a stdio MCP command now run the image's system Python during the connection test too, instead of the AutoSecOps virtual environment. The probe also caps CPU time, file size, and open files. It does not cap address space, so Node, Java, and .NET servers start as they do in agent runs.

## Roll back

AutoSecOps migrations are forward-only. A release that ran migrations cannot run on an older image: the older migrations step fails with `Can't locate revision identified by '<revision>'`, and the API never starts.

- To roll back a patch upgrade on the same train, set the image tag back to the earlier patch and restart. Patches contain no migrations.
- To roll back any other upgrade, restore the pre-upgrade backup, then deploy the previous version.

Agent runs that started on the newer version and are still open, such as runs waiting for a tool approval, can include steps the older version does not recognize. On the older version, Temporal retries their workflow tasks without making progress, and the runs resume after you upgrade again. Before an image-only rollback, let open agent runs finish or cancel them.

On Docker Compose:

```bash
cp docker-compose.yml.bak docker-compose.yml
cp Caddyfile.bak Caddyfile
# Set AUTOSECOPS__IMAGE_TAG in .env back to the previous version
./restore_compose.sh /var/backups/autosecops/autosecops-backup-<timestamp>
docker compose up -d
```

Data written after the backup is lost, including cases, workflow runs, and settings. On Kubernetes, restore the database and buckets, then run `helm rollback autosecops <revision>`. On Fargate, restore the pre-upgrade RDS snapshot as described in [Backup and restore](/self-hosting/backup-restore#aws-fargate), then apply with the previous `TF_VAR_autosecops_image_tag`.

## Kubernetes

Upgrade with `helm upgrade` and the new chart version. See [Upgrade the Helm chart](/self-hosting/kubernetes#upgrade-the-helm-chart). Take a database snapshot first.

## Terraform deployments

AWS Fargate deployments of AutoSecOps are configured using Terraform. Take manual RDS snapshots first, as described in [Backup and restore](/self-hosting/backup-restore#aws-fargate). Then extract the Terraform stack from the new image version, set the Terraform variable `autosecops_image_tag` to that version, and run `terraform apply`. See [Updating AutoSecOps on Fargate](/self-hosting/aws-fargate#updating-autosecops) for the full steps.
