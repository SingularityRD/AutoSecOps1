## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/tutorials/aws-get-started/install-cli)
- AWS credentials configured for your target account and role
- A public [Route53 hosted zone](https://aws.amazon.com/route53/) (domain and hosted zone ID)
- `openssl` and AWS CLI (if using the helper secret script)
- Read access to the AutoSecOps packages on GHCR, granted by SingularityRD

## Extract the Terraform stack

Every AutoSecOps image ships the Fargate Terraform stack in `/opt/autosecops/fargate`.
Copy it out of the image version you deploy into an empty directory:

```bash
# 1. Pull the AutoSecOps image
docker pull ghcr.io/singularityrd/autosecops:1.0.0

# 2. Copy the Terraform stack out of the image without starting it
mkdir autosecops-fargate
id=$(docker create ghcr.io/singularityrd/autosecops:1.0.0)
docker cp "$id":/opt/autosecops/fargate/. autosecops-fargate/
docker rm "$id"

cd autosecops-fargate
```

## Registry credentials

ECS pulls the private AutoSecOps images from GHCR with the same GitHub username and token you used for `docker login`. Store them in Secrets Manager and pass the secret ARN to Terraform:

```bash
aws secretsmanager create-secret --name autosecops/ghcr-pull \
  --secret-string '{"username":"<github-username>","password":"<read-packages-token>"}'

export TF_VAR_autosecops_registry_credentials_arn=<secret-arn>
```

Terraform adds `repositoryCredentials` to every AutoSecOps container and lets the execution roles read the secret. If you encrypt the secret with a customer-managed KMS key, also grant the execution roles `kms:Decrypt` on it. When you rotate the token, update the secret value; ECS uses it on the next image pull. To pull from your own registry instead, mirror the images to Amazon ECR, set `autosecops_image` and `autosecops_ui_image`, and leave `autosecops_registry_credentials_arn` unset.

## Initialize and deploy

Initialize Terraform and apply the configuration.
`auth_superadmin_email` has no default — if you leave it unset, no one can sign in to the new deployment.

```bash
terraform init

export TF_VAR_aws_region=<aws-region>
export TF_VAR_domain_name=<domain>
export TF_VAR_hosted_zone_id=<hosted-zone-id>

export TF_VAR_autosecops_db_encryption_key_arn=<secret-arn>
export TF_VAR_autosecops_service_key_arn=<secret-arn>
export TF_VAR_autosecops_signing_secret_arn=<secret-arn>
export TF_VAR_user_auth_secret_arn=<secret-arn>
export TF_VAR_auth_superadmin_email=<email>

# Optional but recommended
export TF_VAR_autosecops_image_tag=1.0.0

terraform apply
```

Provisioning takes about 10-20 minutes due to RDS and ECS startup.

## Updating AutoSecOps

Read the release notes and take manual RDS snapshots first, as described in [Backup and restore](/self-hosting/backup-restore#aws-fargate). Migrations are forward-only, so rolling back a release that ran migrations means restoring those snapshots.

To update an existing AutoSecOps deployment on Fargate:

1. Extract the Terraform stack from the image version you are updating to into a new directory.
2. Copy your Terraform state into it, along with any `.tfvars` or override files you created. Skip the state file if you use a remote backend.
3. Set `TF_VAR_autosecops_image_tag` to the same image version and run `terraform apply`.

```bash
# 1. Extract the new stack next to the current one
docker pull ghcr.io/singularityrd/autosecops:<version>
mkdir autosecops-fargate-<version>
id=$(docker create ghcr.io/singularityrd/autosecops:<version>)
docker cp "$id":/opt/autosecops/fargate/. autosecops-fargate-<version>/
docker rm "$id"

# 2. Carry over your Terraform state
cp autosecops-fargate/terraform.tfstate autosecops-fargate-<version>/
cd autosecops-fargate-<version>

# 3. Set variables as before, then update the image tag
terraform init
export TF_VAR_autosecops_image_tag=<version>

terraform apply
```

## Database roles

The services connect to RDS as the non-owner `autosecops_app` role, so tenant row-level security applies to them. Terraform generates its password into Secrets Manager, and the API task's migrations container creates the role as the RDS master user before the API starts. `rls_mode` defaults to `enforce`. On the first apply after upgrading, worker tasks that start before the API migrations finish fail to authenticate and ECS restarts them. See [Database roles and tenant isolation](/self-hosting/security#database-roles-and-tenant-isolation) to verify isolation.

## Temporal payload encryption

`temporal_payload_encryption_enabled` defaults to `true`, so the services encrypt workflow inputs, results, and failures before they reach the Temporal database. Unless you pass `temporal_payload_encryption_keyring_arn`, the services use a keyring Terraform generates in Secrets Manager with a random key ID and root secret, and Terraform grants the API, worker, executor, and MCP task roles `secretsmanager:GetSecretValue` on it. The `temporal_payload_encryption_keyring_arn` output names the secret; back it up with the other platform secrets.

Terraform generates the root secret once and keeps it in state, so later applies never rotate it. The state then holds the root secret, as it already holds the database passwords, so keep the state backend encrypted and access-controlled. To rotate, edit the secret in Secrets Manager as described in [Rotate the keyring](/self-hosting/security#rotate-the-keyring); Terraform ignores changes to its value.

Terraform keeps the generated keyring while `temporal_payload_encryption_generate_keyring` is `true` (the default), whatever you set for `temporal_payload_encryption_enabled` or `temporal_payload_encryption_keyring_arn`, so existing encrypted history stays readable. To retire it after moving to your own `temporal_payload_encryption_keyring_arn`, copy its keys into your keyring, then set `temporal_payload_encryption_generate_keyring = false`. Terraform then deletes the secret with a 30-day recovery window. Do not turn generation back on to recover it: Terraform would create a different keyring, and history encrypted under the old one stays unreadable. Restore the deleted secret in Secrets Manager instead.

### How encryption turns on

ECS replaces the services one at a time, so during an apply old and new tasks run side by side. A task without the keyring cannot decode a payload that an upgraded task encrypted, and the Temporal SDK fails that activity attempt. Many AutoSecOps activities run with a single attempt, so the workflow fails with it. Terraform therefore turns encryption on in two steps:

1. On a new stack, every task starts with the keyring, so encryption is on from the first apply.
2. On an existing stack, the first apply gives every service the keyring with encryption still off, and records the rollout in the SSM parameter path `/<name_prefix>/autosecops/temporal-payload-keyring-rollout`. The `temporal_payload_encryption_active` output is `false`. Wait until the services are stable (`aws ecs wait services-stable`), then run `terraform apply` again: the rollout marker is present, encryption turns on, and the output reads `true`.

Pointing the stack at a different keyring ARN starts the two steps again. If your stack already encrypted payloads with your own `temporal_payload_encryption_keyring_arn` before you upgraded, set `temporal_payload_encryption_assume_keyring_rolled_out = true` so the first apply keeps encryption on.

Terraform detects an existing stack by listing ECS clusters and reads the rollout marker from SSM Parameter Store, so the identity that runs Terraform needs `ecs:ListClusters`, `ssm:GetParametersByPath`, and permission to manage that SSM parameter.

To keep an existing stack storing payloads in plaintext, set `temporal_payload_encryption_enabled = false`. See [Updating](/self-hosting/updating#temporal-payload-encryption).

## Temporal DB SSL enforcement

For the bundled Fargate `temporalio/auto-setup` deployment, `temporal_db_force_ssl` defaults to `false`:

```bash
export TF_VAR_temporal_db_force_ssl=false
terraform apply
```

This setting applies only to the bundled Temporal RDS instance. It requires a DB reboot when changed and permits non-TLS connections to the Temporal database for compatibility with the current Fargate Temporal auto-setup flow.

If you are using Temporal Cloud or another external Temporal cluster, set `disable_temporal_autosetup=true` and point `temporal_cluster_url` at your external cluster. In that setup, `temporal_db_force_ssl` is typically unused because the bundled Temporal RDS instance is not created. If you run your own external Temporal PostgreSQL and want SSL-only enforcement there, set `TF_VAR_temporal_db_force_ssl=true`.

## High availability

The defaults run two tasks each of the API, worker, executor, and agent worker, one RDS instance per database, and one ElastiCache node. For a deployment that survives the loss of an Availability Zone, apply the opt-in profile in `examples/ha.tfvars.example`. It runs two tasks of every stateless AutoSecOps service, including the UI and Caddy (`ui_desired_count` and `caddy_desired_count`, default `1`), adds a Multi-AZ RDS standby (`rds_multi_az`) and a Redis replica with automatic failover (`redis_num_cache_clusters = 2`), and roughly doubles the RDS and ElastiCache cost.

The bundled Temporal server and Temporal UI stay single tasks. While ECS replaces a lost Temporal task, which takes minutes, no workflow runs. For zone-loss tolerance, use Temporal Cloud or your own highly available Temporal cluster, as described above: set `temporal_cluster_url` and `disable_temporal_autosetup=true`.

```bash
cp examples/ha.tfvars.example ha.tfvars
terraform apply -var-file=ha.tfvars
```

ElastiCache always runs with TLS, encryption at rest, and a password for the application user; the stack disables the default user.

## Log retention

The ECS tasks log to the CloudWatch Logs group `/ecs/<name_prefix>`, which rotates and stores the logs. Set `log_retention_in_days` (default `30`) to the retention your policy requires, e.g. `365`; `0` keeps the logs forever.

## Resource name prefixes

The stack names AWS resources with two prefixes:

| Variable | Default | Applies to |
| --- | --- | --- |
| `name_prefix` | `autosecops` | VPC, ALB, ECS cluster, RDS snapshots, ElastiCache, S3 buckets, CloudWatch log groups, and the Sentry DSN secret. |
| `iam_name_prefix` | `AutoSecOps` | IAM roles and policies, and ECS task definition families. |

Stacks created before the AutoSecOps rename used `tracecat` and `Tracecat`. Set `TF_VAR_name_prefix=tracecat` and `TF_VAR_iam_name_prefix=Tracecat` to keep them on such a stack.

AWS cannot rename these resources in place, so changing a prefix makes Terraform destroy and recreate them, including the S3 buckets and Redis cluster. To move an existing deployment to new prefixes, deploy a second stack with the new prefixes and the same platform secret ARNs, restore the core database from an RDS snapshot with `restore_from_snapshot`, copy the S3 buckets with `aws s3 sync`, verify the new stack, then switch DNS and destroy the old stack.

## FAQ

<AccordionGroup>
  <Accordion title="Is untrusted code execution safe on Fargate?">
    Fargate does not support the permissions model required by `nsjail`. AutoSecOps uses a fallback executor without `nsjail` isolation on Fargate.
    If you need the highest isolation for untrusted code execution (like custom registry actions or `core.script.run_python`), [deploy AutoSecOps on Kubernetes](/self-hosting/kubernetes), where `nsjail` is enabled by default.
  </Accordion>

  <Accordion title="What infrastructure does this stack create?">
    The Terraform stack deploys:
    - Public ALB, Route53 records, and ACM certificates
    - ECS cluster with Service Connect
    - RDS instances (core database and optional Temporal database)
    - ElastiCache Redis
    - S3 buckets for attachments, registry, and workflow artifacts
    - VPC endpoints for S3 and Secrets Manager
  </Accordion>

  <Accordion title="Connecting a VPC-internal LiteLLM, vLLM, or Ollama fails with 'Host is not allowed'">
    AutoSecOps rejects LLM provider and MCP endpoints that resolve to private addresses unless you allow them.
    Set `outbound_allowed_private_cidrs` in your Terraform variables to the endpoint's IP or CIDR, e.g. `"10.0.12.34/32"`, and apply.
    See [Private endpoints](/agents/llm-providers#private-endpoints).
  </Accordion>

  <Accordion title="What happens if database migrations fail?">
    Migrations run in an init container during the API task startup. The API container only starts if migrations succeed. If migrations fail, the deployment pauses and dependent services (`worker`, `executor`) will not update.
  </Accordion>
</AccordionGroup>
