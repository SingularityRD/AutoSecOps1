`support_bundle.sh` collects what SingularityRD support needs to diagnose a problem into one `autosecops-support-<timestamp>.tar.gz`. Attach it to every support request.

## What the bundle contains

| File | Contents |
| --- | --- |
| `summary.txt` | Collection time, host kernel, Docker and Compose versions, or kubectl and Helm release |
| `settings.txt` | Docker Compose only. Every key in `.env`; values only for non-secret settings such as `AUTOSECOPS__IMAGE_TAG` and `AUTOSECOPS__EXECUTOR_BACKEND`, and `<set>` or `<empty>` for everything else |
| `services.txt` | Status of every Compose service, or of the release's pods, Deployments, and Jobs |
| `images.txt` | Image reference and resolved digest of every container |
| `probe.json` | AutoSecOps version, alembic revision, and license status, plan, expiry, and entitlements, read inside the API container |
| `events.txt` | Kubernetes only. Namespace events |
| `logs/` | Recent logs of every service or pod |

The script reads no license key or credential and includes `.env` values only from an allowlist. It passes every collected file through a redactor that replaces known secret patterns with `[REDACTED]`: passwords, tokens, and API keys in key/value pairs, JSON, and escaped JSON; JWTs; private keys; AWS access key IDs; `PASSWORD '...'` literals in SQL statements that PostgreSQL logs; the secret part of webhook URLs (`/webhooks/<workflow_id>/<secret>`); Slack and Microsoft Teams incoming-webhook URLs; presigned URL signatures; and credentials in URLs. The archive is created with mode `0600`.

The redactor matches patterns, so it cannot recognize every secret, and your own workflow and integration logs can contain data your policy treats as sensitive, such as hostnames or user names. Review the archive before you send it:

```bash
tar -tzf autosecops-support-<timestamp>.tar.gz
tar -xzf autosecops-support-<timestamp>.tar.gz && less autosecops-support-<timestamp>/logs/api.log
```

## Docker Compose

Every AutoSecOps image ships `support_bundle.sh` with the other install files in `/opt/autosecops/install`. Copy it next to `docker-compose.yml` if you do not have it yet, then run it from that directory:

```bash
id=$(docker create ghcr.io/singularityrd/autosecops:<version>)
docker cp "$id":/opt/autosecops/install/support_bundle.sh .
docker rm "$id"
chmod +x support_bundle.sh

./support_bundle.sh -o /tmp
```

It collects the last 24 hours of logs, at most 5000 lines per service. Change that with `--since 2h` and `--tail 20000`. If you run several Compose files, set `COMPOSE_FILE` as you do for `docker compose`. The script needs GNU `sed`, which every Linux distribution ships.

## Kubernetes

Run it from any machine with `kubectl` access to the namespace:

```bash
./support_bundle.sh --kubernetes --namespace autosecops --release autosecops -o /tmp
```

`--release` selects the pods labeled `app.kubernetes.io/instance=<release>`. The probe runs in the `api` container of the release's Deployment labeled `app.kubernetes.io/component=api`, whatever the chart named it. Pass `--api-deployment <name>` only if you relabeled it; when no such Deployment exists, `probe.json` says so.

## AWS Fargate

The script does not reach into ECS tasks. Collect the equivalent with the AWS CLI, using your `name_prefix` (default `autosecops`):

```bash
aws ecs describe-services --cluster <name_prefix>-cluster \
  --services $(aws ecs list-services --cluster <name_prefix>-cluster --query 'serviceArns' --output text) \
  --query 'services[].{name:serviceName,running:runningCount,desired:desiredCount,taskDefinition:taskDefinition}' > services.json
aws logs tail /ecs/<name_prefix> --since 24h | ./support_bundle.sh --redact > logs.txt
```

`--redact` applies the bundle's redactor to any text on standard input. Add the AutoSecOps version from `GET /api/info` and the image tag (`TF_VAR_autosecops_image_tag`) to your request.
